# Support Ticket Triage Agent

**What it does:** takes one raw customer support ticket and returns a validated JSON triage result (`category`, `priority`, `summary`, `reason`). It is a small FastAPI service that calls Claude, validates the answer strictly, repairs it once if invalid, and fails with a clear error if that does not work.

## Quick start (exact commands)

```bash
python -m venv .venv
source .venv/bin/activate            # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
cp .env.example .env                 # Windows: copy .env.example .env  -> then set ANTHROPIC_API_KEY
uvicorn app.main:app --port 8000     # start the API
```

In a second terminal:

```bash
curl -X POST http://localhost:8000/triage -H "Content-Type: application/json" \
  -d '{"ticket": "I was charged twice for my Pro plan this month."}'
```

```bash
pytest                               # unit tests, no API key needed
python evals/run_eval.py --update-readme   # eval suite in one command, results appear below
```

Example response:

```json
{"request_id": "a1b2c3d4e5f60718", "result": {"category": "billing", "priority": "medium", "summary": "...", "reason": "..."}, "repaired": false}
```

## The problem it solves

Support teams lose time reading every ticket just to decide where it goes and how urgent it is. This service does that first step automatically, end to end:

`POST /triage {"ticket": "..."}` -> versioned prompt file -> Claude call (retry with backoff + jitter, hard ceiling) -> strict schema validation -> **one** repair call if invalid -> `200` with the result, or a safe `502`/`503` error -> every call logged to `logs/triage.jsonl`.

Categories: billing, technical, account, delivery, refund, other. Priorities: low, medium, high.

## How it is built

| Concern | Where |
|---|---|
| Versioned prompts (not in code) | `prompts/triage_v1.txt`, `prompts/repair_v1.txt`, `prompts/CHANGELOG.md` |
| Validated output, one repair, then clear failure | `app/validation.py`, `app/triage.py` |
| Retries: exponential backoff, jitter, hard ceiling (default 4 attempts) | `app/retry.py` |
| Call log: prompt version, tokens, latency, stop reason | `app/llm.py`, `logs/triage.jsonl` |
| Eval suite (30 labelled cases) | `evals/cases.jsonl`, `evals/run_eval.py` |

Ticket text and raw model output are not logged unless `LOG_RAW_CONTENT=true`.

## Trade-offs and known failures

### Trade-offs
- **Strict parsing costs extra calls.** JSON wrapped in code fences or extra text is rejected and sent to the repair step instead of being silently cleaned. "Valid" stays unambiguous, but 25 of 30 tickets (83.3%) needed a repair call, which adds latency and tokens.
- **One repair, then fail.** No loops. A second invalid answer returns `502` instead of a guess.
- **Small, cheap model** (Claude Haiku 4.5): fast and inexpensive, weaker judgement on priority.
- **Retries only for temporary errors** (connection, timeout, 429, 5xx). Errors like a bad API key are never retried.

### Known failures
- **Only 5/30 (16.7%) answers are valid on the first attempt.** The prompt forbids code fences but the model still adds them. Not fixed yet; a `triage_v2` prompt should be compared against these numbers.
- **Priority accuracy is 23/30 (76.7%).** All 7 misses are the model rating higher than the label (billing, account, delivery and technical tickets marked `high` or `medium` instead of `medium` or `low`).
- **Ambiguous tickets:** priority correct on only 1/3.
- **Non-English ticket:** priority wrong (0/1). One case is a signal, not a measurement.
- **Category accuracy is 30/30, but 30 hand-written cases is a small sample** and does not prove it works on unseen tickets. Run-to-run results vary (an earlier run scored 22/30 on priority).
- Cost is not reported because pricing variables are not set in `.env`.
