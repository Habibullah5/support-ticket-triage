# Support Ticket Triage Agent

**What it does:** takes one raw customer support ticket and returns a validated JSON triage result: `category`, `priority`, a one-sentence `summary` and a short `reason`. It is a small FastAPI service that calls Claude, checks the answer strictly, repairs it once if invalid, and fails clearly if that does not work.
- **Demo Video (3 minutes):** https://www.loom.com/share/your-actual-demo-id
- **Repository:** https://github.com/your-username/support-triage-agent

## The problem it solves

Support teams lose time reading every ticket just to decide where it goes and how urgent it is. This service does that first step automatically, end to end:

`POST /triage {"ticket": "..."}` -> prompt (versioned file) -> Claude call (retry with backoff + jitter, hard ceiling) -> strict schema validation -> **one** repair call if invalid -> `200` with the result, or a clear safe error (`502`/`503`) -> every call logged to `logs/triage.jsonl`.

Categories: billing, technical, account, delivery, refund, other. Priorities: low, medium, high.

## Run it (exact commands)

```bash
# 1. Install (Python 3.11+)
python -m venv .venv
source .venv/bin/activate          # Windows PowerShell: .venv\Scripts\Activate.ps1
pip install -r requirements.txt

# 2. Configure
cp .env.example .env               # Windows: copy .env.example .env
# edit .env and set ANTHROPIC_API_KEY=...

# 3. Start the API
uvicorn app.main:app --port 8000

# 4. Triage a ticket (second terminal)
curl -X POST http://localhost:8000/triage -H "Content-Type: application/json" \
  -d '{"ticket": "I was charged twice for my Pro plan this month."}'
# PowerShell:
# Invoke-RestMethod -Method Post -Uri http://localhost:8000/triage -ContentType "application/json" -Body '{"ticket":"I was charged twice for my Pro plan this month."}'

# 5. Run unit tests (no API key needed)
pytest

# 6. Run the eval suite (one command, needs the key) and write results below
python evals/run_eval.py --update-readme
```

Example response:

```json
{"request_id": "a1b2c3d4e5f60718", "result": {"category": "billing", "priority": "medium", "summary": "...", "reason": "..."}, "repaired": false}
```

## How it is built

| Concern | Where |
|---|---|
| Versioned prompts (not in code) | `prompts/triage_v1.txt`, `prompts/repair_v1.txt`, `prompts/CHANGELOG.md` |
| Validated structured output, one repair, then clear failure | `app/validation.py`, `app/triage.py` |
| Retries: exponential backoff, full jitter, hard ceiling (`RETRY_MAX_ATTEMPTS`, default 4) | `app/retry.py` |
| Per-call log: prompt version, tokens, latency, stop reason | `app/llm.py`, `logs/triage.jsonl` |
| Eval suite (30 labelled cases) | `evals/cases.jsonl`, `evals/run_eval.py` |

Ticket text and raw model output are not logged unless `LOG_RAW_CONTENT=true`.

## Trade-offs (honest)

- **Strict parsing costs extra calls.** Output wrapped in code fences or extra text is rejected and sent to the repair step instead of being silently cleaned. This keeps "valid" unambiguous, but in the last run 25 of 30 tickets (83%) needed a repair call, which adds latency and token cost. Only 5/30 (16.7%) passed on the first attempt.
- **One repair, then fail.** No loops. A second invalid answer returns `502` rather than guessing.
- **Small, cheap model** (Claude Haiku 4.5) for speed and cost, at some loss of judgement on priority.
- **Retries only for temporary errors** (connection, timeout, 429, 5xx). 4xx errors such as a bad key are never retried.

## Known failures

- **Priority is the weak spot: 22/30 (73.3%).** Every priority miss is the model rating *higher* than the label (e.g. a duplicate charge or a password issue marked `high` instead of `medium`). Account tickets are worst at 2/5.
- **Ambiguous tickets:** priority correct on only 1/3.
- **Non-English ticket:** priority wrong (0/1). The sample is a single case, so this is a signal, not a measurement.
- **Category accuracy is 30/30**, but 30 hand-written cases is a small sample and says nothing about unseen tickets.
- **The high first-attempt failure rate** (see trade-offs) is a prompt problem still to fix; a `triage_v2` prompt should be compared against these numbers.
- Cost is not reported because the pricing variables are not set in `.env`.
