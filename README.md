# Support Ticket Triage Agent

## What it does

An automated customer support ticket triage service that takes one raw customer support ticket and returns a validated JSON triage result (`category`, `priority`, `summary`, `reason`). It is a small FastAPI service that calls Claude, strictly validates the answer against a defined schema, executes one repair attempt if invalid, and fails with a clear HTTP error if validation fails.

## Problem statement: one clearly stated problem, end to end

Support teams lose time reading every ticket just to decide where it goes and how urgent it is. This product solves one clearly stated problem, end to end:

`POST /triage {"ticket": "..."}` -> versioned prompt file -> Claude call (retry with backoff + jitter, hard ceiling) -> strict schema validation -> **one** repair call if invalid -> `200` with the result, or a safe `502`/`503` error -> every call logged to `logs/triage.jsonl`.

Categories: billing, technical, account, delivery, refund, other. Priorities: low, medium, high.

## How it is built

| Concern | Where |
|---|---|
| Versioned prompts (not in code) | `prompts/triage_v1.txt`, `prompts/repair_v1.txt`, `prompts/CHANGELOG.md` |
| Validated output, one repair, then clear failure | `app/validation.py`, `app/triage.py` |
| Retries: exponential backoff, jitter, hard ceiling (default 4 attempts) | `app/retry.py` |
| Call log: prompt version, tokens, latency, stop reason | `app/llm.py`, `logs/triage.jsonl` |
| Eval suite (30 labelled cases) | `evals/cases.jsonl`, `evals/run_eval.py` |

Ticket text and raw model output are not logged unless `LOG_RAW_CONTENT=true`.

## Trade-offs and known failures

### Trade-offs
- **Strict parsing costs extra calls:** JSON wrapped in code fences or extra text is rejected and sent to the repair step instead of being silently cleaned. "Valid" stays unambiguous, but 28 of 30 tickets (93.3%) needed a repair call, which adds latency and tokens.
- **One repair, then fail:** No loops. A second invalid answer returns `502` instead of a guess.
- **Small, cheap model:** Uses Claude Haiku 4.5: fast and inexpensive, but demonstrates weaker judgment on priority.
- **Retries only for temporary errors:** Connection drops, timeouts, 429 rate limits, and 5xx errors trigger retries. Client configuration errors (e.g., bad API key) fail immediately without retrying.

### Known failures
- **Only 2/30 (6.7%) answers are valid on the first attempt:** The prompt forbids code fences but the model still adds them. Not fixed yet; a `triage_v2` prompt should be compared against these numbers.
- **Priority accuracy is 23/30 (76.7%):** All mismatched cases are due to the model rating higher than the label (billing, account, delivery, and technical tickets marked `high` or `medium` instead of `medium` or `low`).
- **Ambiguous tickets:** Priority is correct on 2/3.
- **Non-English ticket:** Priority wrong (0/1). One case is a signal, not a measurement.
- **Category accuracy:** Hand-written evaluation cases are a small sample; unseen real-world inputs may vary.
- **Cost is not reported:** Pricing variables are not configured in `.env`.
